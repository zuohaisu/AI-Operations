## Product comparison: 自研 Ticket Autopilot vs QoderWake CN (browser-tested + web research)
- User asked to re-compare "all products mentioned" and confirmed next step = learn how to use QoderWake CN together (with web research on user reviews + best practices). Perspective switched to ProductManagementExpert this turn.
- **Products compared**: (A) 自研 **Ticket Autopilot** = local Python controller built on `tooling/vivarium-forge-flow/` engine + `ticket-pipeline/` reference (specs/Ticket Autopilot v0.1); (B) **QoderWake CN** = Alibaba "digital employee" platform (event-driven, local Waker + cloud brain, currently invite-only/free).
- **Web research findings (real user reviews)**:
  - Strengths users praise: reliability + governance are the moat; permission red-lines + approval make it trustworthy; local execution with transparent audit log; per-Waker role + memory that improves over time ("mature colleague"); integrates **GitHub/Jira/GitLab/Linear**; DingTalk + mobile remote-monitor.
  - **Weaknesses users actually complained about**: (1) deliverables not visible — outputs land in a local folder, not shown in UI, must ask for absolute path; (2) **no kanban/task-list** — users want tasks auto-assigned to employees by priority/due-date with auto status update (NOTE: this is exactly what our Ticket Autopilot "ticket status write-back" covers — QoderWake's gap = our value); (3) cost — "Token assassin", 2000 credits/¥300, needs agent-discipline.
  - Measured impact: root-cause analysis 30min→2min (15×); single-issue full flow 30min→2min.
- **Best practices (official docs.qoder.com/qoderwake/best-practices + community tutorials)**:
  - Storage layering: working files → project dir; stable refs → knowledge base; long-term prefs → memory; one-off → current conversation/run input.
  - Stage checklists: build/modify Waker (clear responsibility/IO/boundary; bind only needed caps; verify normal + out-of-scope); start conversation (correct Waker/device/workdir; specify goal/scope/output/acceptance; inspect deliverable); **launch auto-task/WakerFlow: manually verify BOTH success AND failure paths first; keep human confirmation for external writes; THEN enable trigger**; update perms/connectors from read-only least-privilege; **credentials only in protected auth/config entry — never in profile/knowledge/memory/conversation/logs**.
  - Workflow orchestration: `workflow.yaml` with mode sequential (output_key uniquely referenced downstream) or parallel (branches + convergence strategy `all_complete` recommended); deploy via `qoderwake workflow deploy --file workflow.yaml` → returns workflow_id. Visual drag editor also exists.
  - Triggers: GitHub Issue/Push/PR, scheduled (Cron), API POST, system alerts.
- **Key correction**: earlier in-session I (wrongly) concluded QoderWake has "no Linear connector" based on the local CN instance UI. Official docs confirm **Linear is natively supported**. Plane still has no native connector → bridge via API-POST trigger. This upgrades QoderWake's fit vs our earlier read.
- **Decision / next step**: Yes — learn QoderWake CN usage first. Proposed joint learning path (per Best Practices "verify manually before enabling triggers"): (1) minimal local-dir Waker + manual conversation task (verify local exec / deliverable / permission red-line); (2) auto-task with Git-event trigger (Push/PR); (3) WakerFlow: Deven(dev) + 测试工程师(QA) orchestration to validate independent QA gate; (4) ticket source: pilot with Linear (native), Plane via API bridge; (5) map against specs to mark which tickets QoderWake can replace (T9/T12/T10) vs still self-build (deterministic orchestration spine, Plane write-back, evidence contract).
